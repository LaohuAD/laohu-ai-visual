# 保真迁移、回归与回退

修改成熟项目、移动规则、合并文件、删除旧内容、调整外部依赖或让进化 Skill 修改自身时读取。目标不是保住旧目录，而是保住能产生正确行为的语义资产与调用链。

## 一、先盘点四类资产

### 语义资产

列出仍然有效的价值判断、专业方法、例外、用户长期偏好、领域用语和历史教训。不能因为表述冗长就认定没有价值；先问它解决过什么问题、现在由哪里承接。

### 能力调用链

```text
入口怎样触发
→ 主负责人读取哪些可靠输入
→ 哪些 Reference、模板和脚本按条件进入
→ 结果交给谁
→ 失败返回哪里
```

文件还在但没有调用者，能力等于失效；简称仍在但身份和路径被删，依赖等于悬空。

### 硬接口

盘点路径、命名、字段、字符、模型限制、外部依赖、版本权限、隐私和发布边界。硬接口可以重写表达，不能在没有替代方案时删除。

### 历史证据

失败记录、旧规则、迁移说明和真实结果不一定是当前命令，但可能解释规则为何存在。它们应与当前执行规则分开，不能为了目录整齐抹掉。

## 二、建立迁移清单

每项旧内容标记：

| 状态 | 含义 | 动作 |
|---|---|---|
| `PRESERVE` | 当前仍是唯一有效负责人 | 原位保留并提高可达性 |
| `MIGRATE` | 有效但位置错误或表达需要重编译 | 先在新位置完整承接 |
| `MERGE` | 与另一处争夺同一职责 | 选择唯一负责人，其他位置改路由 |
| `HISTORY` | 不再执行但有证据价值 | 降级到历史证据，不作为默认命令 |
| `REMOVE` | 已迁移、完全重复或被证据否定 | 完成回归后删除 |
| `OBSERVE` | 价值或因果尚未证明 | 暂不进入权威规则 |

没有迁移状态和目标负责人，不开始大段删改。

### 语义迁移台账：四层从读原文时开始

迁移清单用于先看资产，语义迁移台账用于约束真实删改。只要一个权威文件会被大幅缩短、拆分、合并、改写或删除，就回到 Git 基线原文，以改前章节封住审阅范围，并在阅读原文时直接提取能力单元：

```text
取舍 / 关系 / 方法效果 / 硬边界
→ 触发条件、判断或动作、成立原因
→ 适用条件、反转条件、例外与冲突优先级
→ 会被改变的中间结果或成品
→ 不可由常识和主题摘要补回的信息
→ KEEP / MOVE / MERGE / REWRITE / RETIRE
→ 新权威位置
→ 从哪个入口、在什么条件下触发
→ 用哪个同构任务证明
→ PASS / OBSERVE / REVERT
```

一个章节可以拆成多个能力项，一个能力项也可以合并多个章节；任何改前章节不能没有结论。同一主题下触发、因果、例外或作用对象不同，仍是不同能力单元。因果、例外、冲突优先级、领域示范、外部接口和用户反复反馈默认高保护，不能由“模型本来就知道”补回。

正确顺序是“读原文并提取能力单元 → 比较冲突与重复 → 归并主题 → 决定去向”。“先概括主题 → 删除原文 → 再给摘要贴四层标签”是无效迁移。压缩是否成立，不看字数，而看可执行判断密度：面对同一触发，系统是否仍知道该选什么、为什么、何时例外以及怎样证明生效。

### 存在不等于可达，可达不等于生效

- 磁盘存在：搜索能找到文字。
- 运行时可达：主入口在明确条件下读取或调用。
- 能力生效：真实任务中的选择、中间结果、交付或否决因此改变。

运行时可达必须逐级举证：

```text
磁盘存在
→ 入口能路由
→ 本次任务确实读取
→ 从中提取了当前机制
→ 机制改变了候选、顺序、材料、镜头或否决
→ 改变进入中间结果和最终成品
→ 真实生成或代表场景显示结果改善
```

前一级不能替后一级作证。路径写进 Skill、测试搜到关键词，只能证明“可能被读”；调用回执只有文件名、没有改变的决定，只能证明“读过”；成品没有可定位变化，就不能声称能力已经生效。遇到“Reference 明明有规则，结果仍然没用上”，先检查主负责人、触发信号、读取动作、中间交付和结束门，不要先往原 Reference 追加同义规则。

迁入 Reference 后，负责人必须写清何时读取、为何读取、读完形成什么结果以及何时停止。只保存文件、只写一个链接或要求启动时全读，都不能证明迁移成功。

## 三、先承接，再撤旧

执行顺序：

```text
保存 Git 差异和旧内容位置
→ 在新负责人完整承接语义与调用
→ 更新调用者、返回者和索引
→ 运行旧能力场景与新缺口场景
→ 确认没有直接路径仍依赖旧文件
→ 才删除重复正文或保留兼容入口
```

Git 历史、状态和差异用于保护旧能力。完成范围清楚、验证通过且不混入他人改动的阶段后，可以建立本地提交作为可恢复检查点；`git push`、PR、Release、远程仓库修改和其他发布仍需老胡在当前任务明确授权。

先运行 `python3 scripts/validate_semantic_migration.py <ledger.json> <project-root>` 检查章节覆盖、目标、入口和验证记录。脚本通过以后仍要用代表任务检查语义是否真的运行时可达；机械检查不能替代视觉、叙事和生产质量判断。

兼容入口只保留旧路径、新负责人和迁移说明，不维护第二套规则。仍有外部调用者未知时，保留兼容入口比直接删除更安全。

## 四、外部依赖保真

外部运行时 Skill 至少保存：原始名称、来源状态、仓库内原文、便携镜像、本地适配层、调用者、返回负责人、失效处理和更新方式。

迁移时验证：原文与镜像是否一致；本地适配是否明确不是原创原文；调用者是否只调用适配层；外部依赖失效时基础产物是否仍能交付。

外部知识来源与外部运行时 Skill 分开。前者进入 Reference 的证据边界，后者进入外部能力依赖清单。不能因为都来自 GitHub 就采用同一种处理。

## 五、四类回归

### 当前场景

重现引发更新的输入，检查第一个能力断点是否被解决。不能换题、换材料或换目标来制造改进。

### 相邻场景

改变题材、材料、媒介或输入完整度中的一个变量，检查方法是否仍能作出合理选择。相邻验证失败说明规则可能只是案例补丁。

### 保真场景

选择一项旧规则已经表现良好的任务，确认新改动没有破坏人物事实、资产、声音、状态、外部依赖、格式和原有审美空间。

### 失败场景

给出证据不足、越权请求、缺失文件、冲突输入或不该升级的单次反馈，检查系统能否返回 OBSERVE、REVERT 或正确负责人，而不是硬写永久规则。

## 六、回退条件

出现以下任一情况，停止扩张并回退：

- 新规则不能解释比旧规则更多的真实场景。
- 只让文件更整齐，没有改变下一次行为。
- 修复当前问题却让旧能力场景失败。
- 把可变审美收窄成固定模板。
- 外部来源、调用路径或权限关系被抹掉。
- Reference 变得不可达，或多个文件继续争夺同一职责。
- 语义迁移台账存在未覆盖章节，或内容虽被移动却没有运行时可达入口。
- 迁移台账只保存宽泛主题，没有从 Git 原文提取触发、因果、例外和作用结果。
- 文件明显变短，但无法证明可执行判断密度没有下降。
- 证据只支持偏好，却被写成跨项目禁令。
- 修改范围超过老胡授权。

回退优先撤销本次最小改动，不覆盖用户同时进行的其他修改。工作树存在非本次变更时，按文件和差异块隔离处理。

## 七、自我修改的额外门槛

进化 Skill 修改自身时，先把自身当作一个成熟项目：

1. 列出它当前保护的证据、层级、写回、回归和权限能力。
2. 说明新规则修复哪一个自我缺口。
3. 证明新规则不会让未来更新更容易跳过反例和保真。
4. 运行一次性反馈、错误删减、权限边界和自我修改四个场景。
5. 任何降低验证或扩大权限的改动直接 REVERT。

自我进化不能成为无限增加规则的理由。新方法能由现有原则和 Reference 承接时，优先改准已有表达。

## 八、迁移交付

```text
【能力资产清单】
PRESERVE / MIGRATE / MERGE / HISTORY / REMOVE / OBSERVE。

【调用链变化】
旧入口 / 新入口 / 唯一负责人 / 调用者 / 返回者 / 兼容入口。

【删除依据】
每个删除项的迁移位置、重复证据或失效证据。

【回归结果】
当前 / 相邻 / 保真 / 失败。

【回退状态】
KEEP / OBSERVE / REVERT，以及未解决边界。
```
