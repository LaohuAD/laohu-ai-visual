**把 `.agents/skills/` 整理成"目录层级 = 调用层级"的结构，让 AI 拿到用户一句模糊指令后，能一次路由到正确的方法文件。**

```text

4. 每个文件的信息量和信息密度不下降    → 整理不等于删减
```

**这不是一次内容创作任务，是一次文件整合任务。** 现有内容只搬运、只合并、只删除多余，**不重写**。

## 四、必须理解的四个概念（不理解就会做错）

### 4.1 目录层级 = 调用层级（递归语法，不是固定三层）

```text
某业务技能/
├── SKILL.md         本层意图理解、专业判断、引导、调用、整合
├── references/      直接放本层真实资料文件（方法、案例、合同）
├── skills/          有真实下层能力时才建立；每个子技能同样可有 SKILL.md 与 references/
├── scripts/         有真实工具才保留
├── assets/          有实际资源、数据或配套许可才保留
└── agents/          有宿主配置才保留
```

部门入口、内部专业与更下一级专项使用同一条递归规则。父子关系必须有专业意义：父层提供方向、已有知识和约束，子层继承并深化，不为对称给每条枝增加同样深度。

**判断某个能力该不该独立成层或成文件**（本轮口径）：

```text
有稳定任务、可靠输入、独占判断、明确输出和独立验收 → 值得独立
只在同一判断内换选项，或换掉它其余部分仍原样成立 → 留在原文件内成章节
数据源与派生应用数据 → 按数据关系保存，不按方法去重合并
```

**不再使用的旧判据**：固定只能有三层；只按“会不会被本包以外调用”“被两个以上专业读”这类引用次数一刀切决定拆并。引用次数只是线索，不是判决；一个完整且有独立阅读时机的方法即使只服务一个技能也可以独立成文件，一个术语被多处使用也不因此必须单独建文件。

**用户的原话表述（保留原意）**：「Skill.md 和 Reference 和 skills 这几个东西是并行的；Reference 文件下面只有一个对应的指导文件；skills 下面才会有 SKILL.md 和 Reference 文件，甚至再有 skills 目录。」

### 4.2 四层能力是**功能归属**，不是四个固定标题

权威定义在 `.agents/skills/laohu-ai-visual/skills/laohu-capability-evolution/references/02_四层能力重编译.md`：

> **四层是能力完整性的判断方式，不是四个固定标题，也不是每次更新都要填满的表格。**

| 层 | 承载 | 判断问题 |
|---|---|---|
| **灵魂 SOUL** | 价值、方向、取舍 | 什么值得追求、舍弃或保护发生变化了吗 |
| **筋骨 STRUCTURE** | 负责人、关系、顺序、状态、调用链 | 章法不是步骤表，而是整个能力怎样接力 |
| **血肉 CRAFT** | 材料选择、专业方法、条件、效果因果 | 完整技法六步（见下） |
| **表皮 FORM** | 格式、字段、路径、参数、工具、硬边界 | 不把审美偏好写成机械强制 |

**血肉层的完整技法六步（逐项都要有）**：

```text
触发条件
→ 材料承担的关系、情绪、信息或功能
→ 候选材料或方法的比较
→ 为什么选择这一种
→ 它如何改变可见、可听或可执行结果
→ 什么情况下保留原稿或换用其他方法
```

**材料选择四判据**：因果承重、典型性、媒介可见性、实现与维护代价。

**关键推论——判断一句话留不留，标准不是"是不是总结"，而是"它服务哪一层"：**

```text
方向句  「临界点越具体，张力越大」       → 灵魂层（择优梯度）→ 必须保留
表现句  「临界时刻＝话快骂出口、门快关上」 → 血肉层（可见证据）→ 必须保留
复述句  「信息差就是各方知道的不一样」     → 四层都不服务     → 删除
```

前几轮犯过的错：拿"复述句"的判据去砍了"方向句"。**方向句是灵魂层，删掉 AI 就失去了往哪个方向推的判断依据。**

**伪箴言信号（灵魂层反向检查）**：换到任何项目仍然成立；删掉后不影响选择；需要长篇说明才知道它在说什么；只是禁令换行；只有气势，没有因果。

### 4.3 识别**意图**，不是识别**用户的话**

**错误做法**：把"触发"写成用户原话清单（「这人形不好看」「比例怪」「衣服不贴身」）。

**为什么错**：每个人表达方式不同，同一个意图会有无数种说法，写死在原话上，换个人就接不上。

**正确做法**：触发写**意图类别**。

```text
✗ 用户说「这人形不好看」「比例怪」「衣服不贴身」
✓ 意图＝人物成图的身形／比例／贴合度不成立
```

### 4.4 `SKILL.md` 与 `references/` 的分工

权威依据同上文件：

> **每次必做的专业判断进入 Skill；特定题材、模型、输入状态或失败分支进入 Reference。**

```text
SKILL.md
  ├── 路由：什么意图进来、分派给谁
  └── 本身的功能：本专业每次都必做的那几个专业判断（不是只有路由）

<专业>/references/*.md
  └── 特定题材、特定模型、输入状态、失败分支的方法正文
      写法是【正面描述】：这个东西正确应该怎么做
      负面清单（「不要怎么怎么样」）不归 Reference
```

## 五、整合操作定义

设：`A.md` 文件里包含 A1、A2、A3 三个部分。范围包括 **SKILL.md 本体**和 **Reference 文件**。

```text
情况一：A1 与 B.md 的内容重叠，或 A1 本来就该归 B
  → 把 A1 的内容【融合】进 B
  → B 的信息密度、信息量因此变大
  → A.md 里减少 A1 这部分

情况二：A 里某部分（如 A2）没有任何文件承接，
        但它被多处调用、值得独立
  → 拆成一个独立文件

情况三：A1 哪都不归，只有 A 会用
  → 留在 A，不动
```

### 5.1「融合」的准确含义

**不是原文倾倒。** 搬过去时必须融合进目标文件原有的结构：

- **编号冲突要重排**（原文件里的"8."搬进新文件后不能还叫 8）
- 语序、衔接、层级可以调整
- **不变的是：信息量、信息密度、原本的意图和内容**

**这不是"文字一字不改"，是"信息一字不减"。** 这两件事必须分清。

### 5.2 判断口诀

```text
先看谁会读 → 只有一个专业读、且没有独立阅读时机就并进去
并进去会串味 → 在该专业 references/ 下新建一个主题文件
方法有独立触发、输入、判断、输出与验收 → 可以独立成文件（即使只有一个专业读）
现有目录能承接 → 不新建
一次性产物   → 不留
```

## 六、判断标准

### 6.1 每个文件怎么判

```text
有独立的触发、输入、判断、输出与验收 → 独立成文件
只服务同一判断内的选项              → 并进该专业已有的 reference
并进去后主题变混                    → 在该专业 references/ 下新建
现有目录能承接                      → 不新建
一次性产物                          → 不留
```

“被两个以上专业读”是拆并的线索，不是判决；引用次数不单独决定文件去留。

### 6.2 每句话怎么判

```text
服务灵魂（方向、取舍）        → 留
服务筋骨（负责人、顺序、调用链）→ 留
服务血肉（触发、材料、表现、反例）→ 留
服务表皮（字段、路径、参数）   → 留
四层都不服务（同义复述）      → 删
```

### 6.3 新建文件的准入条件（满足其一，并要求确实存在独立价值）

```text
1. 有稳定任务、可靠输入、独占判断、明确输出与独立验收
2. 有独立的阅读时机，换掉它其他部分仍然成立
3. 现有负责人无法自然承接，且不新增平行规则来源
```

### 8.1 先出方案，再执行

**不要边做边定结构。** 先把整个文件梳理一遍，出一份方案，方案确认后执行只是照做。

### 8.2 方案必须包含

```text
6. 消费者旧链接 → 计算后的新相对链接
```

**路径写法（本轮口径）**：清单、方案和操作卡里的路径相对仓库根；真正写进 Markdown 的链接相对于该 Markdown 所在目录；脚本内部基于 `__file__` 或显式解析的仓库根。不使用绑定某台电脑的绝对路径，也不覆盖用户级全局规则；二者的共同目的是让任何机器与位置都能解析到同一个文件。

### 8.3 最终交付

```text
1. 整理后的真实文件系统
2. 一份完整目录树，列出每个文件，无省略
3. 一份实施记录：改了什么、为什么、验证结果、未完成项
```

## 九、验收标准

```text
结构
  五包与既有专业父子关系保持（不搬技能树）
  references/ 下不再出现 skills/、内置方法树或副本树
  没有空目录、没有只有一两句话的新文件
  每个非根技能的入口写明所属父级的相对链接

内容
  同一件事只在一个文件写一份，其余位置只保留可解析读取地址
  每个文件的原有信息量、信息密度没有下降，规则强度没有漂移
  每条规则能归属到四层之一

工具
  路径校验通过（python3 scripts/validate_skill_packages.py）
  副本审计通过：旧同步器不再生产副本，报告真实维护入口（T01 后的 scripts/sync_skill_packages.py --check）
  回归测试通过（python3 -m unittest discover -s tests）
  合法跨包相对链接可解析到唯一正文，不被单包校验误判（T02）

交付
  完整目录树已刷新（scripts/update_skills_readme_tree.py）
  实施记录已写（04_诊断与系统日志/现有架构细化_实施记录.md）
  操作清单已记录源—目标—章节—状态—验证（04_诊断与系统日志/全库整理操作清单.json）
```

“五包分别复制到项目外仍可独立工作”不再是本轮验收项：独立调用某项能力与隔离一个文件夹离线自足是两件事，本轮不为隔离上传保留运行副本。

## 十、禁止事项

```text
禁止重写现有内容
      整合是搬运、合并、删除，不是重新创作

禁止把"信息不变"理解成"文字不变"
      编号、语序、衔接可以调；信息量、信息密度、意图不能减

禁止自己发明新的写作规约和模板
      项目已有判断方式（四层能力），用它的

禁止把所有反馈都变成永久规则
      先判断是一次性修改、当前任务规则、项目级规则还是长期偏好

禁止边做边定结构
      先出完整方案，确认后执行

禁止用绝对路径或只说文件名
      项目文件内部用相对路径；向老胡说明位置时用仓库根相对路径；
      迁移后重算入向、出向、脚本与注册表引用，不用全局字符串替换补 `../`

禁止用 git add -f 绕过 .gitignore
      作品项目、私人素材、生成媒体不进 Git

禁止为了显得系统化而创建目录和文件
```
