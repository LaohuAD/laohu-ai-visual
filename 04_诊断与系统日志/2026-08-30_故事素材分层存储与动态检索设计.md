# 故事素材分层存储与动态检索设计

## 一、要改变的真实结果

当长期素材从数条增长到数万条时，正式编剧仍只读当前缺口需要的少量候选；原始素材、故事原子、使用历史与本地检索索引分权，任何一层的增长都不得迫使 AI 加载整库。

这次不把“一页返回多少条”升级成创作配额。单页只是上下文边界，总检索量由剧本缺口、因果方向覆盖与新候选的边际增益决定。

## 二、已确认的问题

当前单 JSONL 方案已经通过工具投影避免把整库直接发给 AI，因此 token 隔离并非完全失效。但它仍有六个长期断点：

1. `stats / search / get / write` 每次都在本地读取并校验整库。
2. 每次追加都重写整个权威文件。
3. `source / atom / usage` 混在同一故障域。
4. 读取 atom 详情时默认连带完整 source，越过真实需求。
5. 压缩索引仍返回大段机制、人性和记忆载体，不够像 Skill 表头。
6. `limit=20`、`per_source_limit=2`和“通常 3—7 个详情”容易从技术经验滑成创作上限。

## 三、权威分层

```text
00_输入原料/故事素材库/
├── manifest.json
├── index/
│   └── story_material.sqlite3
├── sources/YYYY/MM/SRC-....json
├── atoms/YYYY/MM/ATM-....json
├── usage/YYYY/MM.jsonl
└── legacy/
    └── 初始迁移快照.jsonl
```

- `sources/`：原话单真源，普通检索不读取。
- `atoms/`：故事原子详情 Reference，只按 ID 读取。
- `usage/`：选择、使用与真实结果事件，不回填改写 atom。
- `index/`：可由三类权威文件重建的本地 SQLite 索引，不作长期事实真源，不把整个文件发给 AI。
- `manifest.json`：小型库概况和索引状态，类似 Skill 目录表头。
- `legacy/`：只保留一份迁移前可恢复快照，不参与运行时检索。

SQLite 索引不存储 `source.original`。它只存 atom 一句话核心、可搜索词、关系、职责、情绪、主题、置信度、详情路径与 usage 摘要。

## 四、五层渐进读取

```text
第0层 describe/stats：库规模、分类、长尾展开能力
→ 第1层 search-index：本地查询后返回一页索引卡
→ 第2层 continue-search：缺口未解决时翻页、放宽或转换查询
→ 第3层 get-atom：只读真正入围的原子详情
→ 第4层 get-source/get-usage：只在语气、证据、权利或失败归因需要时读原话与历史
→ 素材负责人编译交接包给编剧
```

`get-atom` 不得默认返回 source 原话。`get-source` 必须显式按 `SRC` ID 调用。

## 五、动态候选与检索会话

检索不设固定的总候选数。每页使用字符预算控制工具返回量，并返回 `session_id / next_cursor / has_more`。单页预算只是工具边界，不得被解释为剧本的素材配额。

每个检索会话保存压缩状态：

```text
作品与范围：story / sequence / scene / beat / texture
当前缺口和素材职责
已读 atom IDs
入围 IDs
淘汰方向摘要
已覆盖的因果方向
仍未解决的缺口
当前 cursor 与查询轮次
```

翻页时 AI 只读“压缩会话状态＋新一页卡片”，不重放前面所有卡片。

来自同一 source 的原子不使用永久固定数量上限。第一轮可用 `balanced` 查看来源差异；当某个 source 在不同剧作职责上仍有价值时，使用 `open` 或显式展开该 source。

## 六、体量和缺口分解

时长不直接决定候选数。长篇叙事按以下层级建立多个独立检索会话：

```text
story：主引擎、核心人物选择、高潮与结尾
sequence：某一段关系、副线或压力怎样升级
scene：一场戏的行动、试探、物件与结果
beat：一次可见可听的触发和状态变化
texture：生活、职业、口语和场景证据
```

长片可以累计考察很多候选，但每个检索会话只处理当前范围。短片允许高密度采用，但验收的是单位时间内观众可完成理解的有效状态变化，不是原子个数。

进入剧本的原子分为三种职责：

- 承重：改变人物选择、关系、故事方向或结尾意义。
- 支撑：用动作、数字、物件或反应证明承重原子。
- 纹理：提供真实口气、职业细节与场景气味。

候选是否充分看：真实缺口是否解决，关键位置是否有因果真正不同的竞争，新一页是否还在产生新方向。当新结果只是换词重复，或只会增加信息却不改变观众状态时停止。

## 七、接口

```text
add-source --input <file>
add-atoms --input <file>
log-usage --input <file>
stats
facet-values --input <field-cursor-budget-file>
search-index --input <file>
continue-search --input <file>
get-session --id RET-...
close-session --id RET-...
get-atom --id ATM-... [--id ATM-...]
get-source --id SRC-... [--id SRC-...]
get-usage --atom-id ATM-... [--atom-id ATM-...]
rebuild-index
migrate-legacy --legacy-db <path>
validate
```

`search-index` 创建会话；`continue-search` 接收入围、淘汰摘要、已覆盖方向与未解缺口后翻页。检索引擎只做结构查询和稳定排序，不自动宣布素材充分。

## 八、迁移、验证与回退

迁移必须保护：

- source 原话逐字一致；
- 所有 SRC / ATM / USE ID 不变；
- atom 到 source 的引用不变；
- 所有字段、创建时间、状态和 usage 历史不变；
- 新索引不含 source 原话；
- 新 `get-atom` 不返回 source；
- 旧库在新库验证通过前不移动；
- 验证通过后，旧库只移入 `legacy/`作为恢复快照，运行时不再读取。

回退条件：原话、ID、引用、使用历史任一不一致；动态分页重复或漏返候选；新库无法从权威文件重建索引；未选中的 source 原话进入 AI 输出；长篇范围无法分立管理。

## 九、决策

采用“文件作权威真源＋SQLite 作可重建索引＋动态分页会话作上下文闸门”的混合方案。它保留当前原话单真源、零采用、外部确认门和项目/库级 usage 分权，只替换不可扩展的存储与读取骨架。
