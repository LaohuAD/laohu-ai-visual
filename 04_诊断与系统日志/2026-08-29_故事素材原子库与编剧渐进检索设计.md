# 故事素材原子库与编剧渐进检索设计

**状态：** 已完成方案确认，待老胡审阅书面设计后进入实施计划。

**适用范围：** 老胡 AI 视觉中的日常灵感、生活观察、短视频案例、对话、社会现象、突发想法和其他可用于故事创作的材料；负责长期积累、渐进检索、编剧调用和使用反馈，不替代正式剧本创作。

**设计目标：** 让老胡亲自筛选的生活与内容素材成为可持续增长的剧本能力：平时一句“记录灵感”就完成原话保存与深度拆解；正式写剧本时先检索压缩索引，再按需读取少量原子详情；内部素材不足时有顺序地放宽条件，仍不足才搜索网络，并由老胡决定外部候选是否进入剧本或长期素材库。

## 一、要解决的根本问题

现有 `laohu-script-writer` 已经能把当前灵感解构成故事种子，但它只解决当前作品，不负责跨作品长期积累。若把每条素材写成完整 Markdown 长卡，再要求编剧每次全部读取，会形成新的断点：

```text
素材越多
→ 单文件正文越长
→ 每次检索读入大量无关分析
→ 相似标签和重复案例争夺上下文
→ AI更容易机械拼接而非准确选材
→ 素材库从创作增益变成上下文负担
```

真正需要的不是“更详细的素材卡”，而是把四件事分开：

1. 原始素材必须完整、只保存一次。
2. 一份原始素材可以拆成多个独立故事原子。
3. 检索先看压缩索引，只有入围候选才读取详情和原话。
4. 素材被使用、验证或否决后，结果要回到同一个长期系统。

## 二、证据、推论与项目取舍

### 已确认事实

- 老胡明确要求：只有出现“记录灵感、保存素材”等触发词时才执行收录；每次收录同时保留原话、深度分析、价值点、标签、底层机制和延展方向。
- 老胡明确要求：每次正式写剧本都必须检索素材库，帮助剧本获得更多真实人类情感、生活细节、场景质感、趣味、信息价值和传播记忆点。
- 老胡明确要求：内部素材不足时先扩大检索范围，仍不足可以网络搜索；外部候选必须说明搜索原因、建议用法和风险，由老胡决定是否采用。
- DB Skills 的公开原子库使用 JSONL：4,176 个知识原子约 2.6MB，每行包含提炼知识、原文、主题、关联 Skill、类型和置信度；这种结构证明“单文件、一行一原子、按字段过滤”能够承载数千条记录。

### 不能直接照搬的部分

- DB Skills 的 `original` 面向推文，默认限制较短；老胡的口述、转录或案例可能很长，不能截断后丢失口气、上下文和真实细节。
- 一条原始案例可能同时包含人物行为、关系错位、台词口气、物件、场景和传播表达，不能被强压成一个原子，也不能为每个原子重复整段原文。
- DB Skills 的主题和 Skill 标签适合商业知识检索，不足以表达故事中的人物关系、剧本职责、记忆载体和情绪运动。
- 全量文件和季度文件并存会产生双真源风险；本项目只保留一个数据真源，索引按需投影，不手工维护第二份数据库。

### 项目价值取舍

- 老胡亲选素材拥有更高策展优先级，但“老胡觉得有价值”不等于事实已经核实。
- 编剧每次必须检索，但允许零采用；不为完成调用动作把不适配素材硬塞进剧本。
- 记忆点追求高价值变化密度，不追求固定秒数或平均分布。呼吸、留白和铺垫可以没有新奇信息，但必须服务后续兑现。
- 网络素材只能成为待审候选，未经老胡确认不得进入剧本或长期正式原子库。

## 三、方案比较与结论

### 方案A：在编剧 Skill 内维护 Markdown 素材卡

- 优点：文件直观，改动少。
- 缺点：采集和写剧本职责混在一起；单条卡片过长；规模扩大后无法渐进加载；编剧默认上下文持续膨胀。
- 结论：不采用。

### 方案B：独立素材 Skill＋单文件 JSONL 原子库＋动态索引

- 优点：采集、拆解、检索和反馈拥有独立负责人；原话只保存一次；索引与详情分层；无需数据库服务；能够用本地脚本机械验证。
- 风险：需要设计稳定字段、查询合同和写入工具；JSONL 不适合直接手工编辑。
- 结论：胜出方案。

### 方案C：SQLite、向量数据库或外部知识库

- 优点：大规模语义检索、并发和统计能力更强。
- 缺点：引入服务、迁移、依赖和维护成本；当前素材数量尚不足以证明需要；会让“先把好素材积累起来”变成技术建设项目。
- 结论：保留为将来真实性能不足时的迁移方向，不在本轮实施。

## 四、负责人和能力边界

### 新负责人：`laohu-story-material`

该 Skill 具备独立触发、输入、判断、输出和验收，满足新建门槛：

```text
独立触发：记录灵感 / 保存素材 / 记一下这个案例 / 这个可以当素材。
可靠输入：老胡原话、生活观察、短视频链接或转录、对话、案例、新闻、突发想法。
独占判断：原始素材怎样拆成故事原子、价值类型、底层人性机制、可见证据、延展、标签、边界和检索职责。
明确输出：source、atom、usage 三类 JSONL 记录，以及素材候选交接包。
独立验收：原话未丢、原子不重复、机制有证据、索引可检索、详情按需加载、外部候选不越权。
```

它不写正式故事和剧本，不决定人物最终选择，不替编剧设计高潮，也不调用图片、视频或发布工具。

### 与现有负责人的接力

- `laohu-ai-visual`：识别触发词，路由采集或编剧检索；维护第十四个执行入口和跨 Skill 合约。
- `laohu-story-material`：写入原始素材、拆解原子、查询、放宽检索、生成外部候选报告、记录使用事件。
- `laohu-script-writer`：先写当前剧本的素材查询合同，消费候选，决定怎样融入人物、因果、场次和记忆点；不直接改原子库。
- `laohu-generation-review`：真实剧本、成片或传播结果回来时定位首断点；涉及素材有效性时把证据交回素材 Skill 追加 usage 事件。
- `laohu-capability-evolution`：只有重复素材结果改变长期拆解、检索或编剧能力时才更新规则；普通使用反馈不直接升级永久方法。

素材是跨作品创作资产，不新增 `IDEA / STORY / ASSET` 等顶层作品状态。source 使用 `active / archived` 保存状态；atom 的有效调用状态由初始 `callable` 状态和素材库级 `paused / reopened` 事件推导。某部作品中的 `rejected` 只说明本次不适配，不能自动停用整个原子。作品状态仍由总控维护。

## 五、唯一数据真源

### 文件位置

```text
00_输入原料/故事素材原子库.jsonl
```

该文件保存私人生活观察、未公开创意和外部案例来源，默认加入 Git 忽略规则，不进入公开仓库。Skill、字段规范、查询脚本和测试可以进入 Git；真实素材数据不能进入测试夹具或共享资产。

### 为什么使用 JSONL

- 一行是一条独立记录，能够追加、流式扫描、按 ID 获取和逐行验证。
- 原始素材、原子和使用反馈可以存在同一个文件，又保持记录职责清楚。
- 第一阶段查询可以只投影压缩字段，不把 `original` 和深度分析交给 AI。
- 不需要手工同步 `INDEX.md`、季度副本或第二份全量文件。

### 写入方式

素材文件只通过本地脚本写入，不直接用模型自由编辑。脚本持有排他写锁，在同目录临时文件中完成整库验证、ID 唯一性检查和新记录追加，写盘成功后以原子方式替换目标文件；失败时保留旧文件，不留下半行 JSON。当前规模仍采用全库校验；只有真实性能证据证明它成为瓶颈时才迁移数据库。

## 六、三种记录

### 1. `source`：原始素材

每次触发至少建立一条 source。它保留老胡完整原话和来源事实，只存一次，不为多个 atom 重复原文。

```json
{
  "record_type": "source",
  "id": "SRC-20260829-001",
  "created_at": "2026-08-29T12:00:00+08:00",
  "original": "老胡输入的完整原话",
  "source_type": "life_observation",
  "source_url": "",
  "source_title": "",
  "fact_status": "personal_observation",
  "curation_priority": "laohu_selected",
  "privacy": "private",
  "rights_note": "",
  "status": "active"
}
```

`source_type` 至少支持：`life_observation / short_video / conversation / news / personal_idea / image / audio / other`。来源未提供时写空或 `unknown`，不猜测补齐。

### 2. `atom`：可复用故事原子

一条 source 可以生成一个或多个 atom。每个 atom 只承担一个可独立检索、迁移和验收的价值核心。

```json
{
  "record_type": "atom",
  "id": "ATM-20260829-001",
  "source_id": "SRC-20260829-001",
  "atom": "一句话说清可复用的故事价值",
  "human_truth": ["嘴硬心软", "自尊防御"],
  "mechanisms": ["用解决实际问题代替直接表达关心"],
  "material_types": ["relationship_detail", "character_action"],
  "dramatic_functions": ["character_setup", "relationship_shift"],
  "memory_carriers": ["action", "object"],
  "relationships": ["父子"],
  "emotions": ["克制", "温暖"],
  "themes": ["家庭", "代际关系"],
  "visible_evidence": ["可见动作或物件证据"],
  "extensions": ["保持机制不变的可迁移方向"],
  "non_replaceable": "删掉后素材会变普通的细节",
  "boundaries": ["不能照搬的台词、人物或标志性组合"],
  "fit": {
    "formats": ["短片", "短剧"],
    "tones": ["现实", "温暖"],
    "roles": ["support", "texture"]
  },
  "fact_confidence": "medium",
  "analysis_confidence": "high",
  "status": "callable"
}
```

字段不追求越多越好。只有会改变检索、适配判断或使用边界的信息才进入 JSON；重复解释、写作过程和空泛赞美不保存。

### 3. `usage`：选择、使用与结果事件

usage 采用追加事件，不回写覆盖 source 和 atom。它记录素材在什么作品中被候选、使用、验证、否决或重新开启。

```json
{
  "record_type": "usage",
  "id": "USE-20260829-001",
  "created_at": "2026-08-29T12:30:00+08:00",
  "atom_ids": ["ATM-20260829-001"],
  "event_type": "used",
  "scope": "project",
  "project": "作品名称",
  "script_position": "第二场人物建立",
  "usage_role": "support",
  "transformation": "保留了什么机制，改变了什么人物和处境",
  "result": "pending",
  "evidence_path": ""
}
```

项目级 `event_type` 支持：`shortlisted / used / validated / rejected`；素材库级支持：`paused / reopened`。`scope` 必须明确为 `project / library`。项目级失败只进入排序证据；只有素材库级事件才能改变 atom 的有效调用状态。当前状态由原始 atom 加后续 usage 事件推导，不为了回填结果重写历史记录。

## 七、四层能力怎样编译成素材字段

四层继续作为内部能力编译器，不在每条记录里机械出现四个栏目：

```text
灵魂
→ human_truth、价值冲突、为什么值得记住、什么取舍不能被改写。

筋骨
→ mechanisms、人物关系、信息差、行动因果、dramatic_functions。

血肉
→ visible_evidence、动作、台词、物件、声音、空间和extensions。

表皮
→ ID、来源、标签、状态、置信度、隐私、版权与usage事件。
```

拆解不是把用户原话改写成抽象道理。每个机制必须能回指 source 中的具体动作、回答、物件、空间关系或结果；只有概念、没有可见证据的 atom 降为待补证，不进入正式可调用状态。

## 八、采集工作流

### 触发门

只在出现明确保存意图时写库，例如：

```text
记录灵感
保存素材
记一下这个案例
这个可以当故事素材
把这一段放进素材库
```

用户只是分享故事、讨论案例或要求写当前剧本时，不擅自长期保存。一次输入同时包含“记录”和“立刻写剧本”时，先保存 source 与 atom，再把素材交给编剧。

### 深度拆解

```text
逐字保存原话和来源
→ 区分事实、推论、感受与未知
→ 判断一份 source 中有几个独立价值核心
→ 每个核心生成一个 atom
→ 提炼人性、关系、因果和剧本职责
→ 找到不可替代的可见 / 可听细节
→ 给出保持机制不变的延展
→ 标记版权、隐私、事实和直接复制风险
→ 机械验证后写入 JSONL
```

默认不因字段缺失打断采集。来源链接、时间或事实无法确定时如实记录 unknown；只有涉及真实人物隐私、违法风险、公开指控或无法辨认用户要保存哪一段时才请求必要确认。

### 回执

写入后聊天只返回：source ID、atom ID列表、最重要的一至三个价值判断、保存路径和可用状态。完整原话与深度字段留在数据库，需要时再读取，不把一次采集变成长篇聊天报告。

## 九、动态索引与渐进加载

索引不是第二个长期文件，而是查询脚本从 JSONL 即时产生的投影视图。

### 第一层：素材库概况

只读取统计与可用范围：总 source、总 atom、可调用数量、主要关系、机制、职责、主题、最近新增和长期未用。该层不输出任何完整原话。

### 第二层：压缩候选索引

按当前查询只返回：

```text
atom ID
一句话 atom
human_truth
mechanisms
material_types
dramatic_functions
memory_carriers
relationships
emotions
themes
curation_priority
fact / analysis confidence
status
历史使用次数与最近结果摘要
```

不返回 `source.original`、详细 `visible_evidence`、全部延展、边界和使用正文。

### 第三层：候选详情

AI 通常先根据压缩索引筛出 3—7 个真正不同的候选，再按 ID 读取完整 atom、关联 source 原话和必要 usage；这不是最低数量门槛。候选数量根据任务职责调整：关键人物选择和高潮需要比较多个因果候选；一个生活动作或场景纹理可能一条强素材已经足够。

### 第四层：创作交接

只有通过人物、因果、语气、事实和边界适配门的候选，才形成素材交接包：保留机制、允许改变、不可复制、适合位置、预期改变和不用它会损失什么。编剧不直接消费整条 JSON。

## 十、编剧强制检索合同

每次正式故事设计、分场、单场次和剧本重写前，`laohu-script-writer` 必须先形成：

```text
当前剧本缺口：
素材职责：主故事 / 冲突 / 人物行为 / 台词 / 场景质感 / 物件 / 记忆点 / 价值信息。
当前人物关系与选择压力：
希望加强的人性机制或情绪：
必须保护的故事事实：
候选需要在哪些因果方向上不同：
怎样算已经充分：
禁止出现的套路与不适配：
```

检索完成后必须留下内部调用回执：检索条件、候选 atom IDs、采用或不采用理由、采用角色、改造方式和对剧本的可观察变化。没有合适候选时可以零采用，但不能省略检索或伪称“素材库无可用内容”。

同一创作任务中，如果人物、故事事实、素材职责和缺口没有变化，可以复用本轮已经生成的素材交接包；进入新的正式创作任务，或上述任一条件改变时，必须重新查询。这样保留“每次正式写剧本先查素材库”的要求，同时避免在同一轮逐句修改时重复加载相同原话。

## 十一、素材充分度与四级扩大检索

充分度判断看“当前剧本缺口是否解决”，不看固定命中数或最终采用数。

### 第一级：严格匹配

优先匹配相同人物关系、人性机制、剧本职责、情绪和可调用状态。已有高适配候选满足当前职责时立即停止。

### 第二级：放宽表面条件

保留人性机制与剧本职责，每轮只放宽人物关系、题材、职业、时代、场景或表现载体中的一项。必须记录放宽了什么，以及为什么仍然同构。

### 第三级：跨领域类比

按相同选择压力、关系错位、信息差、动作结果或情绪运动检索表面不同的素材。候选必须写明可迁移机制、不可迁移细节和当前人物适配证据；只有抽象相似、无法落实到人物行动时淘汰。

### 第四级：内部素材缺口

前三轮仍不能解决时形成：

```text
当前需要什么
已经检索与放宽了哪些范围
候选为什么仍不够
继续由模型自由虚构会产生什么平均化风险
外部研究应搜索什么机制、场景或现实问题
```

只有该判断成立，才进入网络研究。最终只采用一条强素材不构成不足；已有候选因准确而胜出时不为了数量上网。

## 十二、网络素材隔离与老胡确认门

内部素材不足后可以执行只读网络搜索，但搜索结果不直接写入剧本或正式原子库，状态固定为：

```text
external_candidate / not_approved
```

外部候选报告至少包含：

```text
为什么内部素材不足
搜索范围与来源类型
原始内容和可追溯链接
事实、转述、观点或虚构状态
为什么可能适配当前剧本
底层机制与可见证据
建议怎样艺术化改造
不能复制的人物、台词、镜头或标志组合
事实、版权、隐私和误读风险
推荐：采用 / 只作对照 / 不建议
进入当前剧本会改变什么
是否建议进入长期素材库
```

老胡可以选择：

1. 批准当前剧本使用，并进入长期素材库；
2. 只允许当前剧本参考，不进入长期库；
3. 只保留为对照，不进入剧本；
4. 拒绝；
5. 要求继续搜索其他方向。

任何未批准外部候选不得被编剧引用。批准进入长期库时建立新的 source 和 atom，并标记 `curation_priority: laohu_approved_external`；不得伪装成老胡亲历或原始亲选素材。

## 十三、素材优先级与事实可信度分权

```text
curation_priority
→ laohu_selected / laohu_approved_external

fact_confidence
→ high / medium / low / unknown

analysis_confidence
→ high / medium / low
```

策展优先级回答“它是否接近老胡的审美和创作关注”，事实置信度回答“来源能否支持现实声称”，分析置信度回答“当前机制解释有多可靠”。三者不能合并成一个总分。

`ai_external_candidate` 不是正式库内等级。未经确认的网络结果只存在于当前外部候选报告中，保持 `external_candidate / not_approved`；老胡批准进入长期库后才建立 source 和 atom，并改记为 `laohu_approved_external`。

同一次检索中，在适配度相近时优先老胡亲选素材；若亲选素材与当前人物因果冲突，仍然淘汰。网络事实即使可靠，也不能因为权威来源而自动成为好故事材料。

## 十四、记忆点密度与剧本整合

素材不是越多越好，信息量也不等于单位时间塞入更多事实。每个入选原子只允许承担一种主职责：

```text
主记忆点：关键选择、关系翻转、高潮兑现或结尾余韵。
推进记忆点：信息变化、压力升级、微反转或意外回应。
质感记忆点：动作、口气、物件、空间、声音和生活尴尬。
价值记忆点：新理解、现实利益、公共共鸣或传播表达。
```

编剧建立内部记忆点账本：

```text
位置 / 来源 atom ID / 主职责 / 观众状态怎样改变 / 与主线的因果 / 是否和相邻点竞争 / 是否需要呼吸。
```

正式验收看：

- 记忆点是否改变观众理解、期待、关系感受或情绪，而不是只增加新奇名词。
- 主记忆点是否高于支撑细节，高潮是否高于铺垫。
- 相邻素材是否共同推向同一个人物选择和作品承诺。
- 呼吸段是否让信息被消化、情绪沉淀或期待形成。
- 去掉某条素材后是否真的损失人物、因果、场景或余韵；没有损失则删除。

不设置“每几秒一个记忆点”的项目硬规则。短视频可以提高变化密度，长片可以延长铺垫，但密度必须服从观众处理能力、体量、类型和主胜负手。

## 十五、反馈闭环

```text
记录原始素材
→ 拆成原子
→ 编剧检索与入选
→ usage记录改造方式
→ 剧本、成片或传播结果回来
→ generation-review定位是否由素材选择导致
→ story-material追加项目级validated / rejected事件，必要时追加素材库级paused / reopened事件
→ 下一次检索继承真实使用历史
```

真实结果只改变适用条件和排序证据，不删除历史原话。一次作品失败不能直接把原子永久判死：先区分素材本身不成立、放置位置错误、人物不适配、改造丢失机制或下游执行失败。

## 十六、机械工具与接口

为避免多个小脚本和重复真源，计划建立一个工具：

```text
skills/laohu-story-material/scripts/story_material_db.py
```

子命令：

```text
add-source      验证并追加source
add-atoms       验证source引用后追加一个或多个atom
search          输出压缩候选索引，不泄露完整原话
get             按ID读取候选详情、source和usage
log-usage       追加选择、使用或验证事件
stats           输出第一层素材库概况
validate        检查JSON、字段、ID、引用、枚举和隐私边界
```

脚本只处理确定性结构、过滤和投影，不替 AI 判断人性机制、素材价值和故事适配，也不负责网络搜索。

## 十七、失败处理

- JSON 格式错误、重复 ID、atom 引用不存在的 source：拒绝写入，旧文件保持不变。
- 写入中断：临时文件不替换权威文件，报告失败位置。
- 原始素材太长：完整保存，不自动截断；索引阶段永不返回全文。
- 一个原子包含多个可独立机制：退回重新拆分，不靠增加标签掩盖。
- 只有抽象道理、没有原始证据：标为待补证，不进入 callable。
- 内部素材为空或不足：如实生成缺口报告，按四级扩大，不伪造已检索结果。
- 外部候选未经确认：编剧调用硬失败，返回老胡确认门。
- 素材与已确认人物、事实或主题冲突：淘汰素材，不让素材反过来重写作品。
- 数据库文件不存在：首次采集时创建；正式编剧检索时报告“素材库为空”，仍可继续原创，但必须留下无内部素材支持的真实状态。
- 检索返回大量近重复原子：按 source、mechanism 和 dramatic_function 分组去重，优先保留因果不同的候选，不让同一案例拆出的多个 atom 占满候选集。

## 十九、行为验证

### 当前场景

老胡发送一段长口述并说“记录灵感”：完整原话只保存一次；系统拆出多个不重复 atom；聊天返回简短回执；索引查询不泄露原文。

### 相邻场景

- 一句极短生活观察只生成一个 atom，不为字段完整虚构背景。
- 一个短视频链接加转录同时保留来源与原话，原子只吸收机制，不复制标志性台词和镜头组合。
- 纯视觉、声音或物件素材能够成为 texture / motif，不因缺少完整故事被淘汰。

### 编剧场景

- 正式剧本先形成查询合同，从严格匹配逐级放宽；候选足够时停止，不因为只采用一条而上网。
- 内部素材少时可以跨人物关系寻找同构机制；完整原话只为入围候选加载。
- 素材库有候选但均不适配时允许零采用，剧本不被强制改写。

### 外部研究场景

三级检索不足后形成缺口报告并执行只读搜索；外部候选在老胡确认前不能被写入剧本或正式 atom；批准“仅当前使用”时不进入长期库。

### 保真场景

- 已有剧本在不需要素材补强时仍完成检索，但不会因素材库存在而添加无关记忆点。
- 编剧原有观众等待、人物选择、场次压力、候选竞争、VC下游链和作品状态保持不变。
- 真实素材库不进入 Git，测试只用匿名虚构夹具。

### 失败与规模场景

- 非法 JSON、重复 ID、悬空 source、未知枚举、未批准外部候选全部被拦截。
- 以临时生成的数千条夹具验证：第一层和第二层输出不包含 `original`；按 ID只加载目标详情；同源近重复不占满候选；查询失败不改写数据库。

## 二十、完成标准

- “记录灵感”能够脱离创建聊天独立触发、拆解、验证和写入。
- 只有一个 JSONL 数据真源，没有手工维护的重复索引或季度副本。
- 原始素材完整且只保存一次，一条 source 可以拆成多个独立 atom。
- 检索严格执行概况、压缩索引、候选详情和创作交接四层渐进加载。
- 编剧每次正式创作都真实检索，允许零采用，并能证明采用素材改变了什么。
- 素材不足按严格、放宽、类比、外部缺口四级推进，不以固定数量误判。
- 外部候选未经老胡确认不能进入剧本或长期原子库。
- 记忆点有主次、因果和呼吸，不固化为固定秒数。
- 使用结果能够以追加事件回流，不覆盖原始证据。
- 当前、相邻、编剧、外部、保真、失败和规模场景均通过后，能力才可标记 KEEP。
